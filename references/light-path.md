# 轻路径：一页、一个流程的常规活

> 归属：约束满足闭环 · 第 1 步「采集约束」中的轻量单页活约束采集员。
> 本卷只定「单页或单流程怎么快速收拢约束并交付」：新建单页、单个流程，或沿用已定方向继续做，或整页范围内重做时走这条路。轻路径是对完整闭环的简化，不是跳过约束；结论只取「过 / 不过 / 证据不足」。

## 反例

一页落地页做得挺好看，但首屏主角和主动作说不出来；改了三轮才发现方向从头没定。另一头相反的毛病：一页小活也按全量闭环走，六卷参考全读、两轮评审全派，交付说明写了八段——代价远大于这一页本身。轻路径治第二种，不放松第一种。

## 读法

新建单页、单个流程，或沿用已定方向继续做，或整页范围内重做时走这条路。只读入口、本文件，以及入口为这类页面点名的一两份。⛔ 预读参考卷：对应的情况出现了再读。

要比较几个方案、要把概念与主视觉做到极致时，按入口加深——加深只改第 1 步怎样定约束，第 2–5 步照旧。

## 0. 先看项目里已有的约定

项目根有 `DESIGN.md`（或同类的设计约定文件）时先读它，再动手：

- 它写了的（配色、字体关系、圆角、间距、组件用法）照它，不另立一套。
- 它和本 skill 判据冲突时，**照它的，并把冲突写进交付说明**（哪一条、原文、为什么冲突），⛔ 擅自按 skill 改项目。
- 要改这条约定本身，先问一次，拿到「改」再做；没拿到就只提示。

## 1. 动手前写六行

写在回复或设计说明里，不另起文档。哪一行只能写个空泛的说法、落不到具体选择上，说明这一页那处还没想透，先别往下做。这六行就是第 1 步采集约束的产出，每条都得能写成判得真假的句子。

1. **用户与任务**：谁，在什么设备上，来做什么。主视口定一个。
2. **这一页的重点与主要动作**：首屏与每个关键状态各一个重点、一个主要动作，其余动作写明怎样降级。
3. **照惯例的地方与不照做的地方**：这个品类里用户已经期待的结构，照用；再写这页哪一处不照做，以及来自这个产品的理由。说不出理由就不照做。
4. **约束与方向**：一句话，第一眼的感受和整页围绕什么展开，以及必须满足的硬约束。入口为这类页面点名了别的产物时，写在这一行下面。
5. **字体、色彩、主视觉**：字族与字重关系；底色、强调色、由它们派生的选中与描边各是什么，颜色来自这个产品的什么；主视觉是哪张图或哪个图形，来源写清（项目已有／公开素材／生成／代码）。
6. **动效与状态**：主操作的反馈、一处状态切换、首次进入各怎么动；主流程会经过哪些状态（空、加载、出错、成功）。

用户或自己说出「高级」「简洁」「精致」这类词时，先换成上面某一行里看得见的决定；换不出来就不当理由。

需要用户确认时，把第 2–5 行压成三四行发出去，结束这一轮；用户说「你定」「直接做」或无人值守时，写完接着做。**全程只确认这一次。**

## 2. 实现

- 先把这一页或这条流程的主要状态做完，再考虑其他页面。主流程要从入口走到结果，⛔ 只做一个漂亮的默认状态。
- 关键素材先选定或做出来，再围绕它排文字与操作，⛔ 等布局填满以后再补图。
- **分组先用空间，最后才用线**：同组靠得近、组与组留开；还分不清就拉开字号或字重，再不够才换底色。线和框只留给可点的整块卡片、输入框与需要浮起的面板；加框的区域里不再摆加框的小块，留白已经分开的地方不补线，同一处分隔不画两次。
- 颜色、字号、间距、圆角先定成少量变量，后面一律引用。已有项目用它现成的变量、组件与库；问题从源头修，⛔ 把无关重构混进来。
- 内容按真实产品写：名称、数字、时间有长有短，按钮写按下去会发生什么。模拟数据、未接入的动作、生成的图片写进交付说明，⛔ 写在画面上，⛔ 伪造成交、评价与指标。
- 没有工程约束的独立小样用一个 `index.html`，样式与脚本写在里面。

## 3. 截图，看，改

攒一批改动再截，⛔ 每改一处截一次：

```bash
node scripts/take_shots.mjs index.html --size desktop,mobile --out shots
```

只做一端就只截那一端（`--size desktop` 或 `--size mobile`）。要看操作之后的画面，加 `--steps "名字: click .open; fill #name 内容"`，一组出一张。其他用法在 [工具](tools.md) 与 `--help` 里，用到再查。

- **工具报出来的逐条改掉**：它查控制台错误、横向溢出、加载失败的图片、文字对比度、过小的字、过紧的行高、停在透明的内容、手机上会触发页面放大的输入框、要滚动才够得着的弹窗按钮，以及边框分组过多。标准写在工具里，不用背；与画面无关的接口报错记进交付说明，不为它改业务代码。
- **提示清零后再亲自看图**：三秒内说不说得出这一页的重点与主要动作；多行标题、正文与窄屏换行有没有重叠、被裁或孤字；手机上主操作在不在视口里。⛔ 截图存下来不等于看过。
- 界面会存东西的，就走一遍存进去、刷新、再读出来，外加一次存失败。项目里备着验交互的脚本，交付前自己先跑一遍。
- 只跑项目的类型检查与 lint；生产构建与全量测试，用户要求时才跑。

## 4. 一轮独立评审

新界面和整体改版，先把截图自己过一遍，再找个不了解制作过程的评审者来看一轮——单页也一样，材料按 [视觉评审派发协议](visual-review.md) 交。要是页面带着主要操作流程（填表提交、多步流程、会存东西的操作），这一轮再按 [轻量 UX 走查派发](ux-review.md) 加派一人。

拿到报告，从最要紧的那条开始往下修，改完把受影响的画面再自己看一遍。派不出评审者时对着截图自查，交付时写明「未独立评审」。小改动不派。

## 5. 交付

五件事：选定约束与理由；改了什么、哪些没做及原因；做了哪些动效；评审结果与主要问题怎样处理（没派就写原因）；证据文件在任务目录的哪里。建了过程目录时按 [任务工作区](workdir.md) 核对最终改动，⛔ 把过程文件带进正式交付，⛔ 写进 skill 安装目录。

最后按下一节列「接下来可以做」。

## 接下来可以做（收尾菜单）

交付说明末尾列用户接下来能选的事。**不列**：小改动、本轮停在确认点、用户已经说了下一步、无人值守。

- 最多三条，带编号，第一条标「推荐」，末尾加一句「回复编号就行，也可以直接说想改哪里」。
- 只列当前真能做、还没做过的；接后端、接真实服务这类工程任务写进「哪些没做」。
- 每条一句话写清做完能得到什么、要付出什么（多花时间、多耗 token、会新建或改哪些文件、要不要生图）。代价没实测过就用粗略说法，⛔ 编数字。
- 用用户的说法，⛔ 写步骤编号，⛔ 写本 skill 的术语。

| 刚做完 | 候选的下一步 |
|---|---|
| 一个方案的首屏 | 做完整页；换一个方案对比；先生成设计稿再实现 |
| 页面或核心流程 | 沿用这页做其他页面；补动效；换一个方案对比 |
| 只读评审 | 按最重要的两三条建议修改 |
