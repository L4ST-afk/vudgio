# 输入校验的时机（报错与消错）

> 归属：约束满足闭环 · 第 2 步「定判据」——表单字段的反馈时机，判的是**什么时候说话**，不是说什么话。
> 反例：邮箱打到第三个字符就跳红「格式不正确」；用户改对了，红字还挂着，以为没改对；空框一聚焦就报「必填」；一按提交，八个错误同时炸出来，也不知道先看哪。
> 来源：外部主张「reward early, punish late」，落到本卷只取时序与状态，不取话术。

## 一、一句话口径

**晚报错，早消错。** 报错要等用户把这段意思表达完；消错要在改对的那一刻，不等提交、不等失焦。

## 二、状态表（可机判）

| 状态 | 进入条件 | 允许出现错误提示 |
|---|---|---|
| `pristine` | 表单刚出现、用户没碰过、也无预填 | 否 |
| `prefilled` | 出现时已带默认值／URL 回填／扫码值（用户未编辑） | 否（提交时才验） |
| `editing` | 获得焦点并已输入（含程序置值后置焦） | 仅当该字段**已挂着**上一次的错误（见 §四） |
| `blurred` | 失焦（**不问值是否为空**，空值由规则层判） | 是 |
| `submitted` | 点了提交且本字段无效 | 是，且与首个错误字段同时到位 |
| `dirty-after-submit` | `submitted` 后又编辑该字段 | 是；改对即撤，其余字段错误与汇总同步刷新 |

判据：① 同一字段在 `pristine`／`prefilled` 与**未报错的** `editing` 下出现错误样式（红描边、红字、抖动）即不合格——**例外见 §三.4**（拒收型拦截不算错误样式）；② 程序置值（URL 回填、扫码、整表粘贴）不经 `editing` 直接进入校验，必须有入口，⛔ 让状态机停在 `pristine` 却带着非法值。

## 三、四类规则，四种触发

1. **格式可判型**（邮箱、手机号、日期、金额）：`blurred` 才判，打字途中不判。理由：半截的 `a@` 永远不合法，边打边判等于全程报错。
2. **必填**：`blurred` 且值为空才判；空框聚焦、光标还在里面时⛔ 不判。`submitted` 才判空的，只留给「不离开字段就能提交」的单字段路径（搜索框、验证码单框）。
3. **前提已被他字段确定**（结束早于开始、确认不一致）：可在用户没碰后一字段时提前判，但**错误必须落在后一个字段上**，⛔ 标在前一个字段。
4. **字符本身进不去**（手机号框里的字母、日期框里的「2 月 30 日」）：按**输入约束**处理——`inputmode`／字符过滤／整 token 拒收，值根本进不去，就**没有「错误态」可判**；给一次拦截提示即可。⛔ 不要「先让它进来、再报红」：那会把正确实现判成违反 §二判据。

实现三条：

- **跳过组字中间态**：`compositionstart` 到 `compositionend` 之间不判（拼音串、假名阶段框内是字母）。判据是「非组字中 ＋ 已归一化 ＋ 整 token 判」，缺一条就可能误报。
- **先归一化再判**：全角转半角、去空格与分隔符、国家码与本地号分开取。粘贴 `+86 138-0000-0000` 应先清洗成合法值，⛔ 直接判「含字母与符号」。
- **拒收要能撤回**：拒收时保留原值并提供「改成可用字符」的提示，⛔ 静默吞掉用户刚敲的那个键。

## 四、消错

- 一旦某字段进入错误态，此后该字段的 `editing`／`dirty-after-submit` **每键复查**：改对即撤掉错误样式与文案，不等失焦、不等提交。
- 异步校验（用户名占用、券码有效）四件必须齐：
  1. **取消**：新请求发起时 `AbortController` 取消上一个，序号只作双保险；
  2. **比当前值**：回包结论只对「发出时的值」有效，回来时值已变则丢弃——只比序号不够；
  3. **失败态**：超时／断网回「无法校验，请重试」，⛔ 当通过、⛔ 永久停在「检查中」；
  4. **提交前 settle**：提交时若仍有在途校验，等最后一次回包，或把该字段按「未验证」拦下并提示。
- 防抖 400–600ms 为起步区间（可按项目调），⛔ 当硬阈值；同值复用缓存，改回原值不该再抖一次。
- 多规则并列（密码同时要求长度、大小写、符号）：规则清单提前全部展示，命中一条点亮一条；⛔ 一次只报最上面一条，逼用户改八轮。

## 五、位置与形态

- 错误文案在该字段下方，与 label 左对齐，间距同 `space-1`（4–8px）；⛔ 用 toast／弹窗承载字段级错误——它会飘走，用户回头找不到是哪个字段错。
- 错误态不靠颜色单通道：描边＋图标＋文案三者至少两个；色值走警示色，⛔ 借主品牌色当错误色。
- 文案只说怎么改，不重复 label：「请输入 11 位手机号」而不是「手机号格式错误：手机号不正确」。
- 提交失败时一次列全，focus 落到第一个错误字段，并把它滚进视口；⛔ 逐个弹、⛔ 只报第一条。

## 六、不该校验的字段

昵称、称呼、备注一类无格式风险的短文本：不打勾、不实时校验、失焦不报，`submitted` 只判空。校验器装得越多，误报越多，用户对红字的信任越薄。

## 七、验收（六条走一遍）

1. 在格式字段里逐字输入到合法值：全程无红。
2. 清空必填字段后离开：出现一条错误，指向该字段。
3. 带着错误改对：错误在按键当次消失，不等失焦。
4. 留两个错直接提交：两条同时出现，焦点在第一个，汇总与按钮状态同步。
5. 用拼音输入法在数字框里打「shou」：组字阶段无红，上屏成字母时按拒收处理并给提示。
6. 断网状态下触发异步校验：出现「无法校验」，⛔ 不出现通过，⛔ 不永久停在检查中；恢复后改一次值，结论随当前值刷新。

## 自检（本卷）

首版 2026-11-20 落地。同日独立复核发现两处自相矛盾：① `blurred` 原写「失焦且值非空」，与「必填在空值时判」冲突 ⇒ 改为失焦不问值、空值交规则层；② 「任何错误样式即不合格」与「当场判」冲突 ⇒ 「当场判」改为输入约束下的**拒收**，并把它排除在「错误样式」之外。同时补齐：组字中间态跳过、粘贴先归一化、异步四件（取消／比当前值／失败态／提交前 settle）、`prefilled`／`dirty-after-submit` 两个迁移、验收 4→6 条。

边界：防抖 400–600ms 与「拒收提示一次」为本机口径，非实测最优值；未在真实表单上做过两臂，只过判据一致性。
